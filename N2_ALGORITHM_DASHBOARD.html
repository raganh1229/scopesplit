Core Design — Zone-First Architecture

Zone matching before item extraction. Each AI call scopes to ~20-50 items within one zone instead of 1,700+ across the full document. This eliminates continuation hallucination, removes the 64K output ceiling risk, removes the HTTP 520 risk, and dramatically improves matching accuracy.

4 logical passes: Pass 1/2 (zone detection) → Pass 3 (zone matching) → Pass 4 (per-zone extraction + matching). Orchestrated via 5 Inngest steps with independent retryability. Temperature 0 on all API calls.

N1 Empirical Constraints (Why N2 Exists)

  • HTTP 520 wall — Claude returns 520 (server error) after ~2 min of generation
  • 64K output token ceiling — ~450-500 line item pairs max per call
  • Continuation hallucination — model fabricated ~400 items to reach self-reported total_count
  • Zone-name drift — paraphrasing zone names corrupts downstream matching
  • Cross-document matching at scale — 1,700 vs 1,700 items is too large for single-call accuracy
  • total_count field — primary driver of fabrication; eliminated entirely in N2
  • Chunk-based extraction works — page-chunked approach proven viable in N1 Phase 8

Error Handling Pattern (Shared Across All Passes)

Every API call follows: JSON Clean → Parse → Schema Validate → Retry on failure

  • JSON Cleaning: Strip whitespace, markdown fences, extract outermost {...} block. New shared utility lib/ai-response.ts (N1 untouched).
  • Schema Validation: Structural checks per pass (required fields, types, non-empty strings). Invalid → retryable error.
  • Truncation Detection: Check stop_reason === "max_tokens" from SDK first (authoritative). Fallback: output doesn't end with } or ].
  • Retry: 3 attempts per chunk/zone with exponential backoff. Most real-world failures are transient.
  • Fan-out: Promise.allSettled so one failing chunk/zone doesn't cancel others. Hard fail if any rejected after retries.

Key Technical Details

Chunking (Pass 1/2): ~10-page sub-PDFs with 1-page overlap. Overlap ensures zone headers at boundaries always visible. Page offset computed per-chunk at merge time: offset = startInternalIndex - firstPagePrintedNumber. Offset stored directly on each zone entry.

Pre-dedup (before Pass 3): Deterministic dedup collapses obvious within-estimate duplicates (e.g. "Common Lobby" + "1st Floor - Common Lobby") via substring/stem matching before Opus sees the list.

PDF memory: Both PDFs fetched once, held in memory. ~5-15 MB each. All sub-PDFs sliced from same PDFDocument — no re-fetches. Total ~50-80 MB for 28 zones. Well under Vercel 1024 MB default.

Concurrency: Cap of 8 parallel Haiku calls (Issue 21). OTPM is the binding constraint at 90K/min. Pass 1/2 and Pass 4 share the Haiku pool but never overlap. Opus has its own pool.

Deterministic Prematch (LZF Step 2): n2-deterministic-prematch.ts. Accepts pre-extracted JSON items (not raw PDF). Confidence threshold 0.90 (tightened from N1's 0.82). Tokenized description similarity (Jaccard + containment), 100+ abbreviation expansions, action-verb synonyms, plural normalization, unit mismatch hard gate. Greedy best-reciprocal matching. MATCH vs MODIFIED based on cost/qty comparison.

splitMispaired: Ported from N1. Scans MODIFIED pairs, tokenizes both descriptions, strips stopwords. Zero meaningful token overlap → split to MISSING + ADDED. Zero-cost safety net.

Pass 1 — Zone Detection, Chunk 1 (Haiku 4.5) — includes format detection

SYSTEM: "You are analyzing a section of an insurance estimate PDF. Your only job is to identify the document format and locate all zone/section headers on these pages. Do not extract line items, costs, or any other data. Return only valid JSON."

USER key instructions:

  • Pages {startPage}–{endPage} with ORIGINAL PRINTED page numbers
  • Task 1: Format detection → "xactimate" | "symbility" | "unknown"
  • Task 2: Zone header identification with 9 rules:
    • Body only — skip ToC/recap/summary
    • Must be followed by line items (evidence requirement)
    • Return evidence_item for each zone (Layer 3 defense)
    • VERBATIM zone names — no abbreviation
    • If duplicate name, report only last occurrence
    • Use original printed page numbers
    • Empty zones array is valid
    • Count approx_items per zone and total approx_items_on_pages

Response schema:

{ "first_page_printed_number": int,
  "format": "xactimate" | "symbility" | "unknown",
  "approx_items_on_pages": int,
  "zones": [{ "name": str, "start_page": int,
              "evidence_item": str, "approx_items": int }] }
Pass 2 — Zone Detection, Chunks 2+ (Haiku 4.5) — no format detection

Identical to Pass 1 except: no format detection task, no format field in response. Same 9 rules. Same evidence requirement. Same JSON schema minus format.

{ "first_page_printed_number": int,
  "approx_items_on_pages": int,

Pass 3 — Zone Matching (Opus 4.6) — single text-only call

SYSTEM: Expert at reconciling zone names across two insurance estimates. Accuracy critical — wrong zone match corrupts all line-item data. Return only valid JSON.

10 Matching Rules:

  1. Same name, separated pages = distinct zones — "Bathroom" p16-19 ≠ "Bathroom" p34-37
  2. Watch for delineators — numbers, floors, directions, type qualifiers
  3. Numbers are sacred — "Restroom 1" ≠ "Restroom 2"
  4. Page span + item count similarity boost confidence — 3 pages vs 18 pages = suspect
  5. Abbreviation vigilance — treat abbreviated forms as potential matches
  6. Canonical = longest/most specific — "1st Floor - Common Lobby" beats "Common Lobby"
  7. Within-estimate inconsistencies — "Common Lobby" + "1st Floor - Common Lobby" = same zone
  8. Never force a match — unmatched is safer than wrong
  9. ±1-2 page = chunk boundary duplicate — use lower start page
  10. 1:many matches valid — "Master Suite" ↔ "Master Bed" + "Master Bath", isMerged: true

Confidence scale: 100 (identical) → 95 (obvious variant) → 90 (clear synonym) → 80 (likely) → 50-79 (possible) → <50 (don't match)

{ "matched": [{ "e1Zones": [{ "zone": str, "pages": [start, end] }],
                "e2Zones": [{ "zone": str, "pages": [start, end] }],
                "canonical": str, "isMerged": bool, "confidence": int }],
  "unmatchedE1": [{ "zone": str, "pages": [start, end] }],
  "unmatchedE2": [{ "zone": str, "pages": [start, end] }] }
Pass 4A — Extraction + Matching, Matched Zones (Haiku 4.5)

SYSTEM: Expert insurance estimate analyst. Extract and compare line items zone by zone. Return ONLY valid JSON.

Two-step prompt:

Step 1 — Extract: Both documents attached for zone "{canonical}". Extract ONLY numbered line items (integer + period). Skip headers, summaries, subtotals, notes. Stop if different zone header encountered. Cost values exact from PDF. Multi-line descriptions → concatenate.

Fields: n (item #), d (description), q (qty string), u (unit code), rm (remove), rp (replace), rs (reset), tx (tax), op (O&P), t (total — rightmost cost)

Step 2 — Match & Classify: MATCH / MODIFIED / MISSING_FROM_ADJUSTER / ADDED_BY_ADJUSTER

  • R&R = Remove & Replace. SF/LF/EA/SY common units.
  • "Detach & reset" ≈ "R&R" for fixtures
  • Similar descriptions + diff costs = MODIFIED (pricing dispute), not unmatched
  • Each item in exactly one pair. Never double-use an item number.
  • Completely different work = NEVER pair, even if only remaining unmatched

Pre-return verification: Every item actually in PDF. All costs exact. Every extracted item appears exactly once.

Pass 4B — Extraction Only, Unmatched Zones (Haiku 4.5)

Single sub-PDF for a zone that exists in only one estimate. Same extraction rules as 4A Step 1. Same fields: n, d, q, u, rm, rp, rs, tx, op, t.

Contractor-only → MISSING_FROM_ADJUSTER (e1 populated, e2: null). Adjuster-only → ADDED_BY_ADJUSTER (e1: null, e2 populated).

Prompt Engineering Principles (apply to all passes)
  • Context framing: Every prompt explains what insurance estimates are and why two exist for the same property.
  • VERBATIM zone names: Character-for-character from the PDF. Floor prefixes mandatory. No abbreviation/paraphrasing.
  • Removed total_count: Primary hallucination driver in N1. Eliminated entirely.
  • Unmatched items are normal: Two estimates will almost never have same item count. Don't force matches.
  • Description similarity matching: "R&R Base cabinets" ↔ "Remove & replace lower cabinets"
  • Total cost as confirming signal: Similar descriptions + different costs → still same item, classify MODIFIED.
  • One-to-one rule: Each item number in exactly one pair.
  • Temperature: 0 on all calls for deterministic output.
  • 1-page overlap: Chunk boundaries include overlap for zone header visibility (code concern, not prompt).
