N3 Pipeline Architecture Dashboard

Status: Live — V1 & V2 verified 100% Scope: Xactimate ↔ Xactimate Models: Sonnet 4-5 (P4, P6, P17) · Haiku 4.5 (P8, P12) Pipeline: 18 phases, DB-centric, fully observable

Core Design Philosophy

N3 replaces N2's monolithic AI-matching approach with a structured scoring and assignment engine. AI is used only for zone detection, line item extraction, and borderline-case adjudication. The vast majority of matching is deterministic code: multi-feature scoring, zone boost/penalty logic, and the Hungarian optimal assignment algorithm.

Key shift from N2: In N2 the LLM was the matching oracle for every pair. In N3 the LLM is the last resort for ~10% of borderline pairs — everything else is scored, ranked, and assigned by code with full observability at every step.

Goals

Phase 4 — Zone Detection

Model: Claude Sonnet 4-5 · Method: PDF chunking + vision · DB: n3_zones

Both PDFs are chunked into ~10-page sub-PDFs with 1-page overlap at boundaries. Each chunk is sent to Sonnet to identify zone headers. Chunks are processed in parallel, then merged and deduplicated into a final zone list with derived page ranges.

Zone Detection Rules

RuleDetail
Evidence requirementZone must be followed by extractable line items — not a table of contents or summary
VERBATIM namesZone names copied character-for-character. No paraphrasing, no abbreviation.
Duplicate namesZone key = (name, startPage). "Bathroom p16" ≠ "Bathroom p34" — both valid distinct zones.
Boundary handling1-page overlap ensures zone headers at chunk boundaries are always captured in at least one chunk.
Zero zones (flat PDF)Synthesize a single "General" zone spanning the entire document.
approxItemsAI estimates item count per zone — used as context signal in scoring and candidate generation.

Phase 6 — Zone Correspondences

Model: Claude Sonnet 4-5 · Method: Text-only zone list matching · DB: n3_zone_correspondences

The two normalized zone lists are compared to find which contractor zones correspond to which adjuster zones. This table drives the zone boost/penalty system in Phase 13 — preventing cross-zone false positives.

Correspondence Types

TypeExample
one_to_one"BEDROOM 2" ↔ "SECOND BEDROOM" (conf: 0.95)
one_to_many"MASTER SUITE" ↔ "PRIMARY BEDROOM" + "PRIMARY BATHROOM"
many_to_one"LIVING ROOM" + "DINING ROOM" ↔ "MAIN LIVING AREA"
Phase 13 impact: The set of "verified" correspondences (confidence ≥ threshold) defines which zone boundaries are authoritative. Any candidate edge that crosses a verified boundary gets the outside_verified penalty (−0.08). Items whose zones have no correspondence get no penalty but also no zone-match bonus.

Phase 8 — Line Item Extraction

Model: Claude Haiku 4.5 · Method: Per-zone sub-PDF document blocks · DB: n3_line_items

For each zone, a sub-PDF is sliced using Phase 4 page ranges and sent to Haiku as a document block. The model extracts all numbered line items within that zone only, stopping at the next zone header.

Phase 11 — Embeddings

Method: pgvector text embeddings · Input: normalizedDescription per line item · Stored for cosine similarity retrieval in Phase 12

Embeddings enable semantic retrieval — finding candidates with similar meaning even when vocabulary differs. This is critical because contractor and adjuster descriptions for the same work often use entirely different words.

Phase 12 — Candidate Generation

Method: Three parallel retrieval sources · deduplicated into n3_candidate_edges

For each contractor line item, three independent methods generate candidate adjuster items. The results are unioned and deduplicated. Each edge records which sources found it — a "source set" used in scoring.

Retrieval Sources

SourceMethodTypical Coverage
semanticpgvector ANN cosine similarity top-K — finds semantically similar descriptions~55% of edges
fuzzy_descriptionToken Jaccard similarity over normalizedTokens — finds lexically overlapping descriptions~30% of edges
ai_proposed_zoneClaude Haiku reviews contractor items zone-by-zone and nominates adjuster candidates from the corresponding adjuster zone~37% of edges
total_similarityDollar amount proximity — finds items with near-identical totals~24% of edges

A typical V2 comparison (100×95 items) generates ~3,700 raw candidate edges. After Phase 13 scoring, ~76% are rejected, leaving ~900 surviving edges for Phase 14+.

Phase 13 — Scoring ⭐

Method: Multi-feature weighted scoring + zone boosts · This is the algorithmic core of N3.

Every candidate edge gets a rawScore (weighted sum of 6 features) and a finalScore (rawScore ± boosts). The finalScore determines whether a pair is auto-matched, evaluated by code, sent to LLM, or rejected.

Feature Computation

FeatureHow Computed
tradeActionSimilarityTrade exact match (0 or 1) × 0.6 + action similarity × 0.4. Trade mismatch caps the sub-score at 0.4 regardless of description similarity.
semanticSimilarityCosine similarity between pgvector embeddings of the two normalized descriptions.
fuzzyDescSimilarityJaccard similarity of description token sets (stop words removed).
totalSimilarity1 − |c − a| / max(c, a). Perfect amount match = 1.0. 2× difference = 0.5. Missing amount = 0.
zoneCorrespondenceSimilarityConfidence of the zone correspondence linking the two items' zones. In-zone = correspondence confidence. No correspondence = 0.
qtyUnitSimilarityUnit compatibility × 0.5 + normalized quantity ratio × 0.5.

Zone Boost System

BoostValueApplied When
ai_proposed+0.057Edge was nominated by Claude in Phase 12 (ai_proposed_zone source). AI zone-awareness is rewarded.
outside_verified−0.080Edge crosses zone boundaries AND both items' home zones have verified correspondences to other zones. Strong deterrent to cross-zone false positives.

Score Formula

rawScore   = (tradeActionSimilarity × 0.25)
           + (semanticSimilarity    × 0.25)
           + (fuzzyDescSimilarity   × 0.20)
           + (totalSimilarity       × 0.15)
           + (zoneCorrSimilarity    × 0.10)
           + (qtyUnitSimilarity     × 0.05)

finalScore = rawScore + Σ boosts
Example — "Texture walls knockdown" (Bedroom 2, $433.20) ↔ "Drywall texture knockdown" (Second Bedroom, $433.20):
tradeAction=1.0 · semantic≈0.85 · fuzzy≈0.72 · total=1.0 · zone=0.95 · qty≈0.90
rawScore ≈ 0.754 + ai_proposed(+0.057) = finalScore 0.811 → HIGH_CONFIDENCE ✓

Phase 14 — Build Components

Algorithm: Union-Find with path compression + union by rank · DB: n3_match_components

All non-rejected Phase 13 edges define a sparse bipartite graph. Union-Find partitions it into connected components. Items with no surviving edges become singletons and surface as MISSING/ADDED in Phase 18. Phase 15 runs the Hungarian independently per component.

Component Size Classification

ClassTotal ItemsPhase 15 Strategy
small≤ 50Exact Hungarian (Jonker-Volgenant O(n³))
medium51–250Pruned Hungarian
large> 250Greedy assignment + repair pass
Typical result: Standard residential comparisons (100 contractor × 95 adjuster items) produce one medium component containing all items. Phase 15 runs a single Hungarian solve over the full 100×95 matrix padded to 100×100.

Phase 15 — Hungarian Assignment

Algorithm: Jonker-Volgenant O(n³) · DB: n3_match_decisions

For each component, a cost matrix is built where cost[i][j] = 1 − finalScore(contractor[i], adjuster[j]). Dummy columns represent "leave unmatched" at UNMATCHED_COST=0.70. Hungarian finds the globally optimal assignment minimizing total cost — not greedy best-first.

Cost Matrix

Dimensions: N×N where N = max(yoursCount, adjCount), padded to square

cost[i][j]:
  i ≥ yoursCount OR j ≥ adjCount  →  UNMATCHED_COST = 0.70  (dummy)
  edge exists between i and j     →  1 − edge.finalScore
  no edge (no candidate pair)     →  NO_EDGE_COST = 1.0  (avoid if possible)

Decision Classification

0.55 ≤ finalScore < 0.75one_to_oneassignmentNo
finalScore < 0.55possibleassignmentYes

Phase 15 Mutual-Best Rescue Pass

After the Hungarian solve, scans all unmatched contractor items. For each, checks if there is an unmatched adjuster item such that both items' highest-scoring non-rejected edge points to each other (mutual-best). If score ≥ POSSIBLE_MATCH (0.55) → rescued as one_to_one with decidedBy: 'mutual_best_rescue'.

Why: The Hungarian finds the global optimum which occasionally sacrifices a locally strong pair to improve overall cost. The rescue pass restores such pairs without violating global feasibility.

Phase 17 — LLM Adjudication

Model: Claude Sonnet 4-5 · Scope: Only possible decisions (score < 0.55) · Cost: ~$0.01–0.02/comparison

All possible decisions are batched into a single Sonnet call. For each pair, Sonnet sees the descriptions, trades, actions, quantities, totals, and the finalScore. It returns match or no_match with confidence and reasoning (max 400 chars).

Post-LLM Mutual-Best Rescue Pass ⭐

Problem: When Hungarian makes a globally-optimal-but-locally-wrong assignment, both items end up in possible decisions with wrong partners. The LLM correctly rejects both wrong pairings — but now both items are unmatched, and their correct mutual-best edge was never evaluated. Phase 15's rescue pass already ran and can't help (it ran before LLM).

Solution — runs after LLM decisions are applied:

  1. Find all contractor-unmatched decisions (yourItemIds non-empty, adjusterItemIds empty)
  2. Find all adjuster items not in any non-empty adjusterItemIds (also unmatched)
  3. For each unmatched contractor, find its best non-rejected edge to any unmatched adjuster
  4. Check mutual-best: that adjuster's best edge also points back to this contractor
  5. If mutual-best AND score ≥ 0.55 → rescue as one_to_one, decidedBy: 'post_llm_rescue'

V2 concrete example: "Texture walls knockdown" (Bedroom 2) ↔ "Drywall texture knockdown" (Second Bedroom). Score 0.811. Both were wrongly assigned by Hungarian → LLM rejected both wrong pairings → post-LLM rescue correctly rescued them as MATCH.

Complete Decision Provenance

decidedByPhaseMeaning
auto_high_confidence15Score ≥ 0.75 — auto-accepted by Hungarian, no human/LLM review
assignment15Score 0.55–0.75 — code-decided, no LLM review
mutual_best_rescue15Was unmatched post-Hungarian; rescued because both sides' best edge is each other

Phase 18 — Persist Decisions

Converts n3_match_decisions to line_items records. For each one_to_one decision, MATCH if totalAmounts are equal, MODIFIED if they differ. Unmatched contractor → MISSING_FROM_ADJUSTER. Unmatched adjuster → ADDED_BY_ADJUSTER. Computes aggregate totals and sets Comparison.status = COMPLETED.
