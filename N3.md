## A.2 — Stack realities N3 must respect

- **Database access is via Prisma**, not raw Supabase SQL. All N3 schema work must produce Prisma migrations and Prisma queries. The Supabase Postgres instance backs Prisma, but app code never opens a Postgres client directly. Migrations live in `prisma/schema.prisma` and `prisma/migrations/`.
- **Auth is Clerk**, not bare `user_id`. Every "user_id" reference in N3 must resolve to `User.id` (UUID), which is itself synced from `User.clerkId` via a webhook. N3 must not assume Supabase Auth.
- **Storage is Supabase Storage** (bucket `estimates`). PDFs only — no raw page text, structured JSON, or LLM-debug payloads are persisted today. N3 introduces three new buckets (`raw-page-text`, `structured-extraction-json`, `llm-debug-payloads`); these are new infrastructure.
- **Orchestration is Inngest** with **one function**, not many. The current `process-comparison-v2` function uses `step.run` and `step.waitForEvent` to compose passes inside one durable function. N3's "many event types" model can either be implemented as additional events in/out of the same function, or as separate functions. Decision required.
- **Inngest event-name convention** is `comparison/<noun>.<verb>` (e.g. `comparison/process-v2.requested`, `comparison/zone-review.completed`, `comparison/match-review.completed`). N3's `estimate.compare.started`, `estimate.extract.pages` etc. must be renamed to match — see §A.5 patch on Page 15.
- **Subscription metering** decrements `User.comparisonsUsedThisPeriod` on every job. N3's vastly higher per-job LLM-call count (extraction + normalization + adjudication) makes per-call cost matter. Track tokens per job (existing `llm_calls` proposal) and surface tier-aware budget exhaustion.
- **Status enum is fixed**: `PROCESSING | AWAITING_ZONE_REVIEW | AWAITING_MATCH_REVIEW | COMPLETED | FAILED`. N3 introduces additional review gates (extraction validation, candidate-edge match review, possible-match review). Either add new enum values (DB migration) or layer N3's gates inside existing PROCESSING.
- **MatchStatus enum** is `MATCH | MODIFIED | MISSING_FROM_ADJUSTER | ADDED_BY_ADJUSTER | GROUPED`. The `GROUPED` value already exists but is unused — N3's group-matching can wire it up without a migration.
- **Existing UI groups by zone with columns**, not by match-category list. N3's "matched / group_matched / possible_match / unmatched" tabs would either replace the current grouped-by-zone view or be added as an alternate filter. UX decision required before implementation.

## A.4 — Why N3 directly fixes two distinct N2 failure modes

The N2 architecture (May 7, 2026 baseline) has TWO empirically-observed failure
modes that motivated this redesign. Both are addressed by N3's structural
inversion. Both are documented as failure-mode entries (§27.10 and §27.11).

### Failure mode #1 — LLM attention-budget recall (May 6, Set3 demolition)

On Set3, Pass 5 (the cross-zone reconciliation Opus call introduced May 6) only
catches **4–7 of 11 expected demolition cross-zone matches** — even though the
missed pairs have:

- Identical totals to the cent (e.g. "Tear off TPO" $4515.84 vs "Strip TPO" $4515.84)
- Trivially synonymous descriptions
- Are sitting in the orphan pool that Pass 5 receives

The May 7 Pass 5 hardening (deterministic prematch in `cross-zone-reconcile.ts`)
recovered 6 of these via a deterministic identical-totals-plus-Jaccard layer
running before the Opus call — confirming that the recall problem is structural,
not a prompt-engineering problem. N3 generalizes this prematch into the full
candidate-generation layer. See §27.10.

### Failure mode #2 — Pass 3 wrong-pairing of trade-bundle zones (May 7, Set3 demolition)

On the same Set3 input, Pass 3 (zone matching) was observed wrong-pairing the
adjuster's `Demolition & Debris Hauling` zone with the contractor's
`General Site Conditions` zone. The cheatsheet expected Demolition to remain
**unmatched** — its 11 items pair via cross-zone reconciliation with the contractor's
per-room demolition entries. Instead, Pass 3 used name-similarity-fails-then-elimination
logic and merged Demolition+General into a 1:many pairing, which:

- Sent Demolition's 11 items to the wrong Pass 4 call (paired against contractor's
  General Site PDF pages, where there are no demolition items to match against)
- Made all 11 items show up as ADDED in the General Site Conditions zone
- **Removed them from Pass 5's orphan pool** — they are no longer "unpaired” in
  N2's accounting, just "paired with the wrong zone.” Pass 5 cannot recover them.

This is the architectural ceiling. Even with a perfect Pass 5, an upstream wrong
zone pairing corrupts items unrecoverably. The bug isn't in any single pass —
it's in the **strict within-zone matching constraint** that ties downstream
accuracy to Pass 3's first-attempt judgment. See §27.11.

### How N3 structurally solves both

N3 inverts the matching strategy:

1. **N2 / Pass 5** asks Opus to *consider every possible cross-zone pair from a
   text dump and pick the few that match*. Opus is over-conservative on this
   task — proven empirically (failure mode #1).
2. **N2 / Pass 4** *requires* zone correspondence to be correct as a precondition.
   Pass 3 errors corrupt items unrecoverably (failure mode #2).
3. **N3** generates candidate edges *deterministically* from the FULL opposite
   estimate using fuzzy/semantic/total/quantity/trade indexes. Verified zones are
   a +score BOOST, not a wall. Every plausible pair is in the candidate set by
   construction — regardless of what Pass 3 says. The LLM only adjudicates the
   ambiguous edges, not the obvious ones. Recall is a property of the indexing
   layer, not of model judgment.

Concretely, both Set3 failure modes evaporate in N3:

- Failure #1 (Pass 5 recall miss): the missed identical-total pairs would be
  generated as candidates in Phase 12 by total-similarity search alone
  (identical totals → ~1.0 score) and auto-resolve at assignment without an
  LLM call.
- Failure #2 (Pass 3 wrong-pairing): cross-zone matches that contradict the
  verified zone graph receive a small confidence penalty (−0.05 to −0.12 per
  §16.2), not silencing. A high-Jaccard, identical-total cross-zone candidate
  would still score above the high-confidence threshold and pair correctly
  — even if Pass 3 stuffed those items into the wrong zone.

This is why the user's claim of "97% accuracy" is plausible *for the right inputs*.
It is not a property of better prompts or a smarter model — it is a property of
*not letting any plausible candidate be invisible to the matching layer*. See
§27.10 (LLM attention-budget) and §27.11 (within-zone-matching ceiling) below.

## A.5 — Open questions for the user before implementation

1. **Schema strategy.** Do we extend the existing Prisma schema with N3's new
   tables (`zones`, `zone_correspondences`, `candidate_edges`, `match_components`,
   `match_decisions`, `llm_calls`, `extraction_warnings`) and **keep `LineItem`
   denormalized as the final output row** (writing `match_decisions` rows as
   audit trail and projecting them down to denormalized `LineItem` rows for the
   UI)? Or do we build N3 with a fully normalized two-side line-item model and
   convert at output time?
2. **OCR strategy.** N3 introduces a discrete page-extraction step that pulls
   raw text out of each page before LLM zone detection. Current N2 sends PDFs
   directly to Sonnet vision. Adding a `pdf-parse` (or Mistral OCR / `unpdf`) text
   layer first would let normalization, classification, and indexing run on text
   instead of vision. This is a major architectural shift that affects cost,
   latency, and accuracy for typed-PDF estimates. Is it in scope for N3?
3. **pgvector / embeddings.** N3's semantic-similarity recall depends on
   embeddings. Supabase Postgres supports pgvector natively. Are we taking on
   that dependency in the v1 of N3, or is semantic search deferred and N3 v1
   relies on fuzzy + total + trade indexes only?
4. **One-to-many UI.** The existing line-item table renders one row per pair
   (or per orphan). Group matches break that — a single row needs to expand to
   show 3 contractor items grouped against 1 adjuster item. Does N3 v1 ship the
   expanded UI, or does it ship matches but render the GROUPED rows in a flat
   "see linked items" link until UI work catches up?
5. **Reverse-retrieval cost.** N3 specifies running candidate generation in
   both directions. For 5,000-item-per-side estimates with 30–75 candidates per
   item, this is up to 750,000 candidate edges before scoring. Each scored edge
   is a row in `candidate_edges` and ~12 floating-point feature values. This is
   a sizable dataset. Acceptable, or do we cap at one direction with a recall
   audit on a sample?
6. **Runner / grader strategy.** The existing `Accuracy Runner` grades by zone
   bucket (group app items by `appZone.canonicalName`, link each bucket to a
   cheatsheet zone, then pair within the bucket). On May 7 we observed this
   produces misleading metrics on N2 output — coverage hit 114% (impossible)
   when zones collapsed and 56% (artifact) when zones split correctly. For N3
   testing this metric will be even less informative because N3's whole point
   is that items can pair across zone boundaries. **Decision needed**: extend
   the existing `compare.js` with a flat description-based comparison mode
   (every cheatsheet item paired to its single best app counterpart by
   description+total, regardless of zone), or build a new `compare-n3.js` that
   replaces zone-bucketing entirely. Either way, this work must precede Phase
   18's accuracy gates — we cannot confirm ≥95% accuracy with a grader that
   double-counts when zones collapse and under-counts when they split.

## A.6 — Holes in the current draft (must fix before build)

These are identified during the May 7 review and should be resolved in the
relevant section before implementation begins. Each is also patched inline at
the relevant page below.

- **§16.2 Score weights.** The weight sum (0.20 + 0.15 + 0.12 + 0.09 + 0.10 +
  0.10 + 0.06 + 0.06 + 0.08 + 0.02 + 0.02 = 1.00) is correct, but boosts of up
  to +0.15/+0.18 make the maximum achievable score 1.18 or higher. Threshold
  semantics (0.90 / 0.75 / 0.60) need to specify whether they apply to the raw
  weighted sum or to a normalized [0,1] score after boosts and penalties. The
  doc currently equivocates.
- **§17.3 Component sizes.** "Generate small combinations (2–5)" for group
  matching has unbounded combinatorics. With N candidates,
  C(N,2)+C(N,3)+C(N,4)+C(N,5) explodes (N=20 → ~21,000 combinations per source
  item; N=50 → ~2.5M). A hard cap is required. Recommended: limit candidate
  pool to top-K by individual edge score (K=8) before generating combinations.
- **§19.3 Group scoring features.** "Combined description coverage" is
  underspecified — is this token overlap, semantic similarity averaged, or
  both? Pick one and define it in §16.1.
- **§16.4 Amount similarity.** The bucketing (`<0.02 → 1.0`, `<0.05 → 0.9`, …)
  is a step function; tiny ratio changes flip the score by 0.15. Convert to a
  smooth function (e.g. `1 - clamp(ratio / 0.35, 0, 1)`) or document the
  step-function intent.
- **§22.1 Extraction completeness.** The doc lists "extraction completeness"
  as a metric but never defines it. App's analogue: does every numbered line
  item from the source PDF appear in `LineItem` output? This is currently
  measured manually via the Accuracy Runner. Spec needs a formal definition.
- **§28 Final Build Checklist.** Mentions "Inngest payloads remain small" and
  "Supabase upserts make retries idempotent" but doesn't reference the existing
  `ComparisonProcessingState` escape-hatch (see N1 doc). Update to align.
- **§16.1 vs §16.2 feature-count mismatch.** §16.1 lists 17 scoring features
  (description_fuzzy_similarity, description_semantic_similarity, item_code_match,
  trade_match, action_match, material_match, object_match, quantity_similarity,
  unit_match, unit_price_similarity, total_similarity, zone_correspondence_similarity,
  page_proximity, sequence_similarity, special_flag_compatibility,
  extraction_confidence, retrieval_source_strength). §16.2's score formula uses 11
  features and combines several (e.g. "trade_action_similarity", "material_object_similarity",
  "quantity_unit_similarity"). Reconcile before Phase 13 — either expand the formula
  to use all 17 with separate weights, or reduce §16.1 to the actual 11 used.
  Current implicit answer leans toward the combined version (cheaper to compute,
  fewer correlated features), but state it explicitly.
- **§15.4 reverse-retrieval double-counting.** §15.4 says "Run candidate generation
  both directions: E1 → E2 and E2 → E1." §15.3 says "Target: 30–75 candidates per
  item." Combined naively, this DOUBLES candidate count to 60–150 per item before
  dedup. The dedup step is essential and underspecified — use `(source_id,
  target_id)` as natural key and union the retrieval_sources arrays so a single
  edge knows it was found by multiple retrieval methods. Spec must clarify
  whether 30–75 is per-direction or post-dedup.
- **§17.1 edge threshold unspecified.** §17.1 says "edges = candidate edges above
  threshold." Threshold not defined here. Implicitly the 0.60 reject line from
  §16.3, but state explicitly. Below-threshold edges should be DROPPED entirely
  before graph construction (not retained as low-confidence ghosts) to keep CC
  splitting clean.
- **Schema tension between Pages 9–14 and §A.1.** Pages 9–14 propose a normalized
  schema with separate `comparison_jobs`, `estimates`, `line_items` tables. §A.1
  vocabulary translation says "keep `Comparison` + `LineItem` denormalized as the
  output rows; new tables only for intermediate state." The Phase 1 entry on Page
  31 currently says "Create migrations for: comparison_jobs, estimates, ..."
  matching the abstract spec, not the App-Specific Note. **Decision required at
  Phase 1 entry**: which schema actually gets built. The App-Specific Note's
  recommendation is binding (per the Build Readiness banner at top of doc) but
  this needs to be stated cleanly in the Phase 1 plan, not implied. Recommend:
  rewrite Phase 1 build list to read "Create Prisma migrations for: `n3_zones`,
  `n3_zone_correspondences`, `n3_candidate_edges`, `n3_match_components`,
  `n3_match_decisions`, `n3_llm_calls`, `n3_extraction_warnings`. Reuse existing
  `Comparison` and `LineItem` for the job + final-output rows.”

### Principle 1
Chunk processing, not match visibility.

Safe:
- extract pages in batches
- generate candidates against full estimate index
- solve connected components independently

- comparing only matching page ranges
- limiting comparisons to isolated zones

LLMs should adjudicate, not brute-force.

Candidate recall comes before candidate precision.

> **[App-Specific Note — Cascade]** App convention is `comparison/<noun>.<verb>`,
> not `estimate.<verb>.<state>`. Existing events (grep `inngest.send` in the repo):
> - `comparison/process.requested` — N1 entry trigger
> - `comparison/process-v2.requested` — N2 entry trigger
> - `comparison/zone-review.completed` — fires when user confirms zones
> - `comparison/match-review.completed` — fires when user confirms zone pairings
>

> - `comparison/process-v3.requested` — entry trigger
> - `comparison/v3.candidates.generated` — fan-out boundary
> - `comparison/v3.components.solved` — assignment phase done
> - `comparison/v3.adjudication.completed` — LLM adjudication done
> - `comparison/v3.extraction-review.completed` — NEW human gate (Phase 10

>
> **Idempotency keys** in the app should align with: `comparisonId` for the
> top-level job, `comparisonId:zoneId` for per-zone work, `comparisonId:edgeId`

> **[Hole identified — Cascade May 7]** With the listed weights summing to
> 1.00 plus boosts up to +0.15 plus penalties down to roughly -0.08 (or
> hard-reject), the achievable raw score range is approximately
> [−∞, 1.15], not [0, 1]. The thresholds in §16.3 (≥0.90, 0.75–0.90,
> 0.60–0.75, <0.60) need to specify their reference domain. Two valid
> choices:
> 1. **Apply thresholds to a clamped & normalized score** (recommended):
>    after computing `raw`, set `final = clamp(raw, 0, 1)` and re-tune
>    thresholds against fixture data. Boosts above 1.0 are wasted but
>    threshold semantics stay clean.
> 2. **Apply thresholds to raw weighted sum after boosts/penalties**
>    (current implicit reading): document the (−∞, 1.15] range and note
>    that high-confidence threshold of 0.90 occupies most of the boost
>    headroom — a pure description-fuzzy match (max 0.20) plus a
>    user-corrected zone boost (+0.15) only reaches 0.35, well below
>    high-confidence, even on a perfect description match. The weights
>    must be calibrated against labeled fixture data before this is
>    used in production routing.
>
> **Calibration requirement:** Either way, the thresholds in §16.3 MUST
> be calibrated against labeled fixture data before they go to production.
> The existing labeled set lives at
> `Accuracy Runner/PDFS/Generated Sets/Set*/Set*_Cheatsheet.md`. Set3 in
> particular contains hand-crafted cross-zone pairings that are gold
> ground truth. The recommended calibration procedure: run candidate
> generation + scoring on Set3, sort all expected-MATCH candidate edges
> by score, choose the threshold that puts the bottom 95% of expected
> matches above the high-confidence line.
>
> **Special-flag hard-reject** also needs explicit specification: "up to
> hard reject" implies a binary post-filter (the edge is dropped before
> assignment) rather than a score subtraction. Recommended: implement
> as a pre-scoring filter so flag-incompatible edges never enter the
> graph at all (saves scoring cost too). Spec in §17.1 must reflect this.

## 17.3 Component Size Handling

Suggested behavior:

Small components (<50):
- exact assignment

Medium components (51–250):
- assignment with pruning

Large components (>250):
- split by strong features
- greedy matching + repair
- ambiguous subcomponents routed to LLMs

Strong split features:
- special flags
- item code family
- trade
- material/object
- verified zone group

> **[Hole identified — Cascade May 7]** "Generate small combinations (2–5)"
> in §19.2 has unbounded combinatorics. With N candidates per source item,
> the number of size-2-through-5 combinations is C(N,2)+C(N,3)+C(N,4)+C(N,5)
> ≈ N⁵/120 for large N. At N=20 that is 21k combinations per source item; at
> N=50 it is 2.5M. **Required cap before generating combinations:** prune
> the candidate pool for the source item to the top-K candidates by
> individual edge score (recommended K=8). This keeps combination count
> bounded at C(8,2)+C(8,3)+C(8,4)+C(8,5) = 28+56+70+56 = 210 per source
> item, scoreable in a single batch call.
>
> **Additional gating:** only generate combinations where every member
> shares at least one of:
> - the source item's verified-zone correspondence graph (per §14)
> - the source item's trade classification
> - the source item's special-flag profile
>
> This further prunes implausible groups before scoring. Combinations
> that fail all three are essentially "random splits with no logical
> coherence" and the LLM will reject them anyway.
>
> **Empirical reference:** the existing N2 pipeline ran into a related
> problem in Pass 5 — sending 13 contractor orphans × 40 adjuster orphans
> (520 candidate pairs) to Opus in a single prompt produced a conservative
> bias toward refusing to pair (only 7 of 11 expected matches caught). N3's
> top-K candidate pruning + per-source-item adjudication is the structural
> reason recall is expected to recover.

## 27.10 Conservative Adjudicator Misses Obvious Cross-Zone Matches

> **[Empirical motivation — Cascade May 7]** This failure mode was the direct
> trigger for the move from N2 to N3 and is documented from production data
> on Set3. It is the strongest single argument for the structural inversion
> N3 represents.

### Cause
A conservative LLM-driven cross-zone reconciliation pass (N2's Pass 5,
Opus 4-7) is asked to scan all unpaired items from both estimates and
nominate cross-zone matches. The prompt is intentionally hesitant
("err strongly on the side of CAUTION"). On 11 expected demolition
cross-zone matches in Set3, the model nominated only 4, even though 7
of the misses had:

- Identical totals to the cent (e.g. "Tear off TPO" $4515.84 vs "Strip TPO
membrane roofing system" $4515.84)
- Synonymous descriptions ("Tear off polyiso" vs "Demo polyiso insulation
2.5 inch")
- Were present in the orphan pool sent to the model

The misses were not rejected below the 75-confidence threshold — they were
**never proposed**. The Opus response had `proposed: 7, rejectedBelowThreshold: 0`.
Conservative-prompted Opus refused to reason about them at all.

### Why this is structural, not a prompt-tuning problem
Recall depends on the model considering every plausible pair. When the
candidate set is "every orphan × every other-side orphan", LLMs sample a
mental subset and miss the rest. No prompt rewrite reliably fixes this for
adversarial input distributions — the failure is in the attention budget,
not in the rule definitions.

### Fix (the N3 architecture)
Replace conservative LLM-driven cross-zone reconciliation with deterministic
candidate generation + scoring + sparse-graph assignment:

- Every plausible cross-zone pair is in the candidate set by construction
  (total similarity, description fuzzy match, trade match, etc. — see
  §15.2 for the full retrieval source list).
- LLM adjudication runs only on edges where deterministic features are
  ambiguous (e.g. competing similar candidates, near-threshold scores).
- Obvious matches (identical totals, identical units, near-identical
  descriptions) auto-resolve at the assignment phase without an LLM call.
- The user-corrected zone correspondence acts as a strong PRIOR (boost),
  not a hard wall — cross-zone matches that contradict the verified zone
  graph are not silenced, they are penalized but still considered.

### Migration note
N2's Pass 5 stays in production until N3 ships and is validated. The
synthetic `CROSS ZONE MATCHES` zone introduced for N2 Pass 5 output is
NOT carried into N3 — N3 files cross-zone matches into the contractor's
home zone (or whichever zone the user prefers, configurable) with a
`crossZoneOrigin: { e1Zone, e2Zone }` field on the row for UI badging.
The N2 synthetic zone was a UI compromise for Pass 5's small accepted-pair
count; N3's candidate-generation approach typically produces enough
cross-zone matches that they're better surfaced in their semantic zones
with badges than corralled into a separate bucket.

### Test gate
N3's Phase 12 must be measured against this exact failure case. Required
gate: on Set3, the candidate-generation phase must include all 11
expected cross-zone demolition matches in the candidate set (recall = 100%
at any K). Anything less means the indexing layer is not the safety net
N3 claims it is.

## 27.11 Within-Zone Matching Constraint Corrupts Items When Pass 3 Wrong-Pairs

> **[Empirical motivation — Cascade May 7, 2026]** This is the second N2
> failure mode that motivated the move to N3 (the first being §27.10).
> Distinct cause; equally fatal at the architectural level.

### Cause

N2 strictly pairs items within a single zone-correspondence pair (Pass 4
is given two PDF zones and asked to extract+match items between them).
This means the upstream zone correspondence (Pass 3) MUST be correct on
the first attempt for items to land in the right comparison.

Pass 3 only sees zone names + page ranges + approximate item counts —
no line-item content. When two zones have low name-similarity, Pass 3
falls back to **process-of-elimination + count-similarity** logic. This
works correctly when totals line up (e.g. Set3's `Lobby + Exam + Records`
(≈27 items) → `Carpentry & Misc.` (≈27 items) is correct elimination)
and fails silently when an adjuster trade zone has no contractor
counterpart but the model has been told 1:many is valid (Pass 3
Rule 10).

Empirical Set3 case (May 7, 2026): with the obvious matches resolved,
the model was left with:
- Adjuster: `General & Site` (~7 items), `Demolition & Debris Hauling` (~11 items)
- Contractor: `General Site Conditions` (~7 items)

The cheatsheet expected `General & Site ↔ General Site Conditions`
(1:1) and `Demolition & Debris Hauling` to remain UNMATCHED on the
adjuster side (its 11 items recover via Pass 5 cross-zone
reconciliation). Pass 3 instead merged Demolition+General into a 1:many
pair against the contractor's General Site Conditions zone. Result:

- All 11 demolition items shipped to the wrong Pass 4 call (paired
  against contractor's General Site PDF pages, which contain no
  demolition items)
- All 11 classified as ADDED_BY_ADJUSTER (since contractor side has no
  matching items in the paired zone)
- All 11 became invisible to Pass 5 — Pass 5's orphan collection only
  scans pairs marked MISSING_FROM_ADJUSTER or ADDED_BY_ADJUSTER WITH
  the assumption they're truly orphaned, not just "paired with the
  wrong zone”. The deterministic prematch caught 6 by identical-total
  matching across zones, but the rest stayed corrupted.

### Why this is structural, not a prompt-tuning problem

The within-zone matching constraint creates a hard dependency: the
accuracy of every line item depends on Pass 3 being right for that
item's zone. Pass 3 has limited information (no line items) and
limited variance tolerance. Even with a tightened Pass 3 prompt that
resolves Set3, the next adjuster PDF with a differently-named
trade-bundle zone will trip the same elimination logic in a different
way. Strict within-zone matching = guaranteed long-tail accuracy
leakage on real-world PDF distributions.

### Fix (the N3 architecture)

Replace the within-zone constraint with global candidate generation:

- Items in any contractor zone CAN match items in any adjuster zone.
- Verified zone correspondence is a +score boost (per §16.2:
  user_corrected = +0.15, user_confirmed = +0.12, AI_proposed = +0.06).
- A wrong-paired contractor item still pairs correctly across the
  Pass-3-imposed zone boundary if its description + total + qty + trade
  signals are strong enough — the boundary is now a hint, not a wall.

Applied to Set3's demolition case: each demolition item has
identical totals to a contractor per-room item, near-identical
descriptions, and same units. The fuzzy + total + trade indexes
generate the cross-zone candidates regardless of what Pass 3 says.
Scoring puts them at ≥0.85 even with a -0.05 "outside verified zone"
penalty. The candidate is matched at assignment time without an LLM
call.

### Test gate

N3's Phase 12 + 13 + 15 must collectively recover ALL items that N2
would have corrupted via Pass 3 wrong-pairing. Required gate: simulate
a deliberate wrong-pairing in the test fixture (e.g. force
Demolition↔GeneralSite in match-review), then verify that N3's
matching still pairs the demolition items correctly via cross-zone
candidate generation. The system must be **resilient to Pass 3
errors**, not just fast on the happy path.

- **Phase 13 (scoring):** top-1 candidate matches the cheatsheet
  expectation for ≥ 90% of items with a clear ground-truth pair.
- **Phase 15 (assignment):** zero one-to-one collisions on the Set3
  fixture. Required by definition of max-weight assignment.
- **Phase 16 (group matching):** every cheatsheet entry tagged MOD-QTY
  whose adjuster side is a single line corresponding to multiple
  contractor lines (rare in Set3, but more common in real estimates)
  is detected by group-matching with status `GROUPED`.
- **Phase 18 (final output):** item accuracy ≥ 95% on Set3, coverage
  = 100%. Item accuracy ≥ 95% on Set1 and Set2. Aggregate accuracy
  ≥ 95% across all generated sets.
- **Phase 21 (large):** synthetic 5k-item-per-side set completes
  end-to-end in ≤ 15 min and at ≤ $0.50 per comparison in LLM cost.

## B.3 Decisions deferred until phase entry

These do not need answers today, but each phase's start gate must
record the chosen answer:

- **Phase 1**: Are `n3_*` tables prefixed (parallel-build discipline)
  or do they live alongside as `zones`, `zone_correspondences` etc.
  (cleaner naming, but couples N2/N3 lifecycles)? **Recommendation**:
  prefix during build, drop the prefix during the N2→N3 cutover commit
  (mirrors how `pipelineVersion` evolved).
- **Phase 3**: Text-first extraction library — `pdf-parse`, `unpdf`,
  Mistral OCR API, or LLM-vision-only? Cost/accuracy/speed trade-off
  benchmark needed. `unpdf` is recommended starting point: pure JS,
  no native deps, works on Vercel/edge.
- **Phase 11**: Embedding model — OpenAI `text-embedding-3-small`
  (cheap, fast, 1536-dim) vs Voyage AI `voyage-3` (more accurate,
  1024-dim). Pin in `package.json`. **Recommendation**: start with
  OpenAI for v1 (already a likely future dependency for executive
  summaries / chat features); switch to Voyage if recall@50 falls
  short.
- **Phase 15**: Assignment algorithm — the Hungarian algorithm is
  O(n³) and exact; auction algorithms are O(n² · epsilon⁻¹) and approximate.
  For small components (<50 items, the common case after CC splitting)
  Hungarian is fine and dependencies-free (`munkres-js`). For large
  components (>500 after splitting), auction is faster. **Recommendation**:
  Hungarian as default with auction as a fallback for components past
  the size threshold.
- **Phase 17**: Adjudicator model — Sonnet 4.6 (fast, default), Opus
  4.7 (high-stakes ambiguity), or per-batch routing. **Recommendation**:
  Sonnet for everything, Opus only for components flagged `ambiguous`
  AND over $5k summed total (high stakes).
- **Phase 18**: UI: replace zone-grouped renderer with category-filtered
  list, OR add category filter as overlay on existing renderer? UX
  decision (user input required — §A.5 question 4).

## B.4 Things this doc does NOT yet address

These are real concerns N3 implementation will hit, but the spec is
silent. Resolve before phase entry:

- **Idempotent re-runs after partial failure**: if a job fails mid-Phase
  12 (candidate generation), how does retry resume? `step_runs`
  idempotency keys help; Inngest's natural step replay helps; but the
  combination needs a written contract. Specifically: candidate
  generation must not re-fetch already-scored edges from the DB on
  resume. Use upsert with `(source_id, target_id, retrieval_source)`
  as natural key.
- **PII / residency**: page text and embeddings contain customer claim
  data. Where do they live? Supabase Postgres in the same region as
  the PDFs? Encryption at rest? (Already handled for PDFs; N3 expands
  the data surface with `raw-page-text` bucket and `n3_candidate_edges`
  rows.)
- **GDPR / right-to-delete**: when a user deletes a `Comparison`, today
  cascading deletes wipe `LineItem`. N3's expanded schema needs explicit
  ON DELETE CASCADE on every new table referencing `Comparison.id`.
- **Inngest function size limits**: a single function with 22 phases
  worth of `step.run` blocks may exceed Inngest's per-function step
  count or function-source size. Plan for splitting into 3–4 functions
  joined by events (e.g. `setup`, `extract`, `match`, `finalize`).
  N2's process-comparison-v2 currently has ~7 step.run blocks plus 2
  step.waitForEvent blocks; N3 expands this 3–4×.
- **Cost ceiling per job**: a tier-aware cap that aborts the job and
  flips `FAILED` if LLM token spend exceeds the user's plan budget.
  No equivalent exists today — N1/N2 are cheap enough that this never
  came up. With N3's larger LLM-call count, this becomes load-bearing.
  Implement against the proposed `llm_calls` table once it exists.
- **Cancellation semantics**: when a user navigates away mid-pipeline
  or deletes the comparison, every Phase 12+ batch in flight must
  short-circuit cleanly. Existing N2 has a comparison-existence guard
  at the top of every step.run; N3 must replicate this in every fan-out
  worker, not just at step boundaries.
- **N3.md as living doc**: like N2_SPEED_CAPACITY_ACCURACY.md, this doc
  is expected to grow an Issues ledger, a session log, and a
  post-mortem section as work proceeds. Its current shape (transcribed
  spec + reconciliation preamble + appendix) is the starting point, not
  the final form.
- **Runner needs flat-comparison mode for honest N3 testing.** The
  existing `Accuracy Runner/lib/compare.js` groups app items by zone
  and matches each bucket to a cheatsheet zone. On May 7 N2 testing
  this produced unreliable coverage metrics (114% when zones collapsed,
  56% when they split correctly). For N3 testing this metric will be
  even less informative because N3's whole point is items pairing
  across zone boundaries — the runner's zone-bucket grader cannot
  measure that. **Action item before Phase 18 acceptance**: extend
  `compare.js` with a flat description-based comparison mode (every
  cheatsheet item paired to its single best app counterpart by
  description+total similarity, regardless of zone), OR add
  `compare-n3.js` that replaces zone-bucketing entirely. Either way,
  this is a **prerequisite for confirming ≥95% accuracy** — we cannot
  validate the headline Phase 18 gate with a grader that
  double-counts when zones collapse and under-counts when they split.
  Estimated effort: ~30 min if we add a parallel mode, ~2 hours for a
  full grader rewrite. Recommend the parallel-mode add (existing
  zone-bucket grader stays for backward compat with N2 result
  comparisons).
- **Calibration fixture set is small.** The Accuracy Runner's `Generated
  Sets` directory currently contains Set1, Set2, Set3, etc. — a small
  hand-crafted suite. N3's scoring layer (Phase 13) needs more labeled
  examples to calibrate the 11–17 feature weights without overfitting
  to Set3. Action item before Phase 13 acceptance: generate or label
  at least 5 additional sets representing common edge cases (large
  estimates, scanned PDFs, Symbility format, mixed format pairs).
  Without this, the Phase 13 "top-1 candidate matches expectation ≥ 90%"
  gate is statistically unreliable.
